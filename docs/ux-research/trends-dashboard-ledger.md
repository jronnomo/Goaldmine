# Recommendation Ledger — `/trends` Trends Dashboard

**Feature:** Weight, calories and macros on one shared time axis, with a drag-selected sub-window and a window aggregate that states its own coverage.
**Issue:** none (solo flow; PRDs `PRD-g1-trends-dashboard.md` + `PRD-g2-apple-health-import.md`).
**Report:** [`trends-dashboard.md`](./trends-dashboard.md)

Stable IDs `UXR-TRENDS-NN` — assigned once, **never renumbered**. Status starts `proposed`. The **implementing PR ticks each row** to `shipped` / `reworked` / `dropped` with a SHA, a `file:line`, or a one-line reason in Evidence.

Rows tagged `tuning⚠` / `decoration⚠` / `a11y` are the ones a future audit cares about most — **confirm them on a real 390px device, in both themes, and against a grayscale screenshot.** Because the palette is iso-luminant (`--accent`↔`--target` 1.16:1, `--accent`↔`--warning` 1.01:1, `--muted`↔`--success` 1.00:1), the acceptance test for every identity row is: **a grayscale screenshot must lose nothing.**

Rows prefixed **⚑ SIGN-OFF** need a founder decision before implementation. Rows prefixed **🔴** are pre-existing defects or hazards surfaced by this research; they are not part of the feature and should be filed independently unless noted.

**Authority note:** where this ledger and `.feature-dev/2026-09-02-trends-dashboard/agents/architecture-blueprint-v2.md` differ, research wins on presentation and the blueprint wins on mechanism. Rows that ask the blueprint to move are marked ⚑.

## Outcome summary — run closed 2026-09-02 at `b44f35b`

**Counts:** 60 shipped · 5 reworked (03, 04, 14, 57, 58) · 2 dropped (59, 60). Twelve rows (03, 04, 08, 12, 14, 20, 22, 37, 53, 64, 66, 67) are **code-complete but visually unverified**: the integrated 390px browser walkthrough never ran (Chrome extension not connected); the pre-merge check was a real headless Chromium touch smoke (4/4 passed, and it caught a genuine bug — Recharts clamps `activeCoordinate` to the plot area, which made a vertical swipe clear the committed window as a near-tap; see UXR-TRENDS-23).

**Calibration:** the `tuning⚠` rows were well-calibrated wherever they stated a range — every provisional value that shipped (selection fill 0.12, dip 0.65/190ms, panel fade 150ms, mount draw 380ms, 1px band separators, 5px rail track, the 90-day per-day rail cap, the 10px slop) landed inside its stated range untouched. The two `tuning⚠` values that moved were both fold geometry: the calorie chart's h-32 fell to the row's own pre-authorized h-28 concession, and the twice-revised clearance measurement (UXR-TRENDS-04) was wrong a third time. `decoration⚠` held up nearly as well — the one rework (the 90d hatch, UXR-TRENDS-14) was the exact failure that row itself predicted, and every rejection (ghost bars, Bullseye) stayed rejected. The research's weakest category was its own 🔴 side-quests: the two fixes it asked for outside the feature (59, 60) did not happen. Two Tech-Lead descopes from this run (G2 §3.2.17 remember-last-import-range; chart-mark deep-links to `/days/[dateKey]`) have no ledger rows and are recorded here only.
